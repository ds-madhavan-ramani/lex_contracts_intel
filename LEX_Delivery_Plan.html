01 — Executive Summary

A question-answering assistant scoped to the contract corpus

LEX gives the MR5 Transition Contracts Team a Streamlit chatbot that, for every Signed & Executed Contract, automatically answers a fixed set of 16 stock questions — contract title, CW number, end date, one-sentence summary, novation/disclosure/termination/auto-renewal clauses, payment regime, securities, price review mechanisms, and more — the moment the contract (and any of its variations, extensions, or novations) is ingested. Users can also ask free-form follow-up questions against the same corpus. Every answer is grounded in the ingested text and carries numbered citations linking back to the source document's URL; the assistant declines rather than guesses when a contract doesn't address a question.

Rather than building a new pipeline, LEX is proposed as a new project instance of project-llm-wiki, the reusable Snowflake Cortex engine this workspace already runs in production as ORG_MM_CHAT. That means most of the ingestion, retrieval, and citation machinery is proven and reused as-is; the real work is a contract-specific segmentation profile, sizing for documents up to 500 pages, a structured extraction layer that persists the 16 stock answers for every contract, contract-family linking across variations/extensions, and a tighter access boundary around a small, named user group.

What's genuinely new: a LEX_CONTRACT segmentation profile tuned to clause/schedule-structured legal text, a chunked-indexing fix for 100–500 page documents (the template's default 150,000-character cap silently truncates anything past roughly 50 pages), a CONTRACT_REGISTER / CONTRACT_FIELD_EXTRACTS layer that persists the 16 stock answers with a per-field citation and a human-verify flag, and an isolated database (LEXDB) + dedicated compute pool (LEX_COMPUTE_POOL) + RBAC role restricting the app to 3–5 people.

02 — Objectives & Scope

Objectives & scope

Goals

  • Answer all 16 fixed stock questions automatically for every contract, the moment it and its variations/extensions are ingested.
  • Let users ask free-form follow-up questions about contract terms, in a concise, professional tone.
  • Ground every answer in retrieved text and always show numbered citations linking to the contract document's URL.
  • Scale from 8 contracts (Build) to roughly 600 contracts, 100–500 pages each (Scale), without a redesign.
  • Restrict use to the MR5 Transition Contracts Team members who need it — not a workspace-wide tool.

RetrievalRAG over the ingested corpus only; no open-web or general-knowledge answers.

Success criteria

  • Only the named 3–5 users can open the app; everyone else's access attempt fails at the Snowflake grant, not in application code.
03 — Solution Approach

Why RAG, and why this engine

Signed contracts are exactly the shape this engine already handles well: a bounded set of long, structured documents where an answer needs to be traceable to one clause in one document, not synthesised from fuzzy keyword hits. project-llm-wiki's retrieval isn't classic chunk-and-embed RAG — it indexes each document into a navigable tree (document → section, each with an LLM-written summary) and lets the model traverse that tree the way a person would use a table of contents, falling back to keyword search and, optionally, embedding search when tree routing alone under-recalls. That combination is what contract Q&A needs: individual contracts are long enough that summary-based routing keeps cost and latency sane, but dense enough — and at 600-document scale, numerous enough — that a second, semantic recall path matters from day one of the Scale phase.

What LEX needs beyond a chat engine, though, is a standing, reviewable answer to the same 16 questions for every contract — not just an on-demand Q&A surface. Rather than building a second, bespoke extraction pipeline alongside the chat engine, LEX runs each of the 16 stock questions as a canned call into the same retrieval engine used for chat, scoped to one contract's document family, and persists the result. This keeps exactly one retrieval/citation/synthesis code path to maintain, and it degrades the same way chat does — "not found in the documents" rather than a hallucinated field (see §06).

Provisioning LEX as a project instance — rather than a bespoke build — means schema DDL, ingestion, indexing, tree search, reranking, caching, and citation rendering are all already written and running in production for ORG_MM_CHAT. Engineering effort concentrates on what's actually different about this corpus: its clause-based structure, its size per document, its multi-document contract families, and its access boundary.

04 — Architecture

How a contract becomes a cited answer — twice over

Component notes

RAW_DOCUMENTSOne row per physical document — the base contract and each of its variations, extensions, and novation deeds are separate rows. Parsed text, SHA-256 hash for idempotent re-ingestion, and SOURCE_URL — this is what makes every citation clickable. PDFs/DOCX go through AI_PARSE_DOCUMENT OCR.
DOCUMENT_INDEXA tree, not a flat chunk store: a root node per document, section nodes underneath with an LLM-written summary each. A NODE_EMBEDDING VECTOR(FLOAT,768) column holds a semantic embedding per section — needed at 600-document scale, where document-summary routing alone is too coarse.
CONTRACT_REGISTER + LINKNew tables. One row per real-world contract (keyed on CW number), with a join table recording which physical documents belong to it and in what role — base, variation, extension, or novation — so free-form Q&A and the extraction job both route across a contract's full history, not just its base document.
CONTRACT_FIELD_EXTRACTSNew table. One row per (contract, stock field) — the persisted, citable answer to each of the 16 questions, re-resolved whenever a new document lands in a contract's family, with a CONFIDENCE rating and an IS_VERIFIED human sign-off flag.
query_engine.pyThree signals feed the section candidate pool: document/section summary routing, a literal keyword fallback for clause numbers and defined terms a summary might not capture verbatim, and (when enabled) embedding similarity search. An LLM reranker narrows the pool before a final synthesis call writes the answer with numbered, deterministic citations — used identically by chat and by the extraction job, scoped by an added restrict_to_doc_ids parameter for the latter.
LEX_APPThe Streamlit front end — the existing Chat.py / Data Sources / Sync Status pattern from ORG_MM_CHAT, plus a new Contract Register page, deployed as its own Streamlit object on a dedicated compute pool, gated by a dedicated RBAC role.

05 — Security & Access

A boundary the platform enforces, not the app

Access control is deliberately kept out of application code — Chat.py has no login screen or user table, and it should stay that way. Restriction happens at the Snowflake grant, the same mechanism that already protects every other object in this workspace:

  • A new role, LEX_USERS, holds USAGE on the LEX_APP Streamlit object and its compute pool — nothing else. It is granted only to the 3–5 named MR5 Transition Contracts Team accounts.
  • The underlying DATA_LEX schema and tables stay owned by ADVANCEDANALYTICS, the same service role every project in this catalog runs as — end users never get direct table access, only the app's query path.
  • A dedicated Graph API app registration's Sites.Selected grant is scoped to just the contracts library, not the whole tenant, and not shared with ORG_MM_CHAT's own registration — revoking LEX's access later shouldn't touch other projects.

Recommended: a fully separate database. LEXDB and LEX_COMPUTE_POOL, following the same precedent already set for FRANK's MEDSGOV / STREAMLIT_COMPUTE_POOL_OCMS_GOVERNANCE in this workspace — neither exists yet for LEX and both need SYSADMIN to create. The template's shared catalog bookkeeping (MEDSOCMS.APP_CATALOG.PROJECTS) still centralizes which projects exist and their settings; only LEX's actual data (schema, tables, stage) moves into LEXDB. That split needs the same DATA_DATABASE template extension FRANK's plan already scoped — implement it once, both projects benefit (see §07 Phase 1).

06 — Answer Quality Design

Concise, cited, and willing to say no

Tone & length

The synthesis prompt (the same call that already numbers citations deterministically and normalises stray formatting artefacts in ORG_MM_CHAT) will be adjusted for LEX to favour a short, direct answer — lead with the answer, follow with the supporting clause language, and stop — written as if briefing a contracts manager, not restating the source text exhaustively.

Citations

Every answer's SOURCE_URL-backed citation list is already numbered and clickable in the existing engine — reused unchanged. Where a contract is long enough that "the whole document" isn't a useful citation, DETAILED segmentation (one section per clause/schedule) is what keeps a citation pointing at the actual clause rather than a 500-page PDF.

A new segmentation profile: LEX_CONTRACT

The existing ORG_MEETING_MINUTES profile is written for minutes. Contracts need a profile written for clause-structured legal text instead: segment by clause/sub-clause/schedule/annexure, quote defined terms, clause numbers, dollar figures, and dates verbatim rather than paraphrasing them (routing accuracy depends on it, exactly as the existing README notes for meeting codes), and flag cross-references to a contract's own variations or extensions where the text makes them. This is a new entry in index_builder.py's PROMPTS dict plus a matching SEGMENTATION_PROFILE catalog value — additive, no changes to the calling code.

The 16 stock questions: canned queries, not a bespoke prompt

Each stock field is generated by calling query_engine.search() — the same function chat uses — once per question, scoped to a contract's full document family via the new restrict_to_doc_ids parameter. The result (answer, source document, source clause, verbatim quote) is upserted into CONTRACT_FIELD_EXTRACTS. This runs automatically when a family is first fully ingested, again whenever a new document lands in an existing family, and on demand from the Contract Register page. For 8 contracts this is instant; at 600 contracts it moves to a scheduled Snowflake Task rather than an inline Streamlit action.

Legal accuracy stakes make an unreviewed LLM answer risky to rely on as-is: every field shows its citation and a CONFIDENCE badge, and a reviewer marks IS_VERIFIED before the team relies on it. "Not found in the documents" is an explicit, valid answer — never a guess.

No memory, by design — for now

Each question is answered independently; there is no chat history fed back into retrieval or synthesis. This matches what the team asked for and keeps every answer's provenance unambiguous. Multi-turn memory is scoped as a future enhancement once the single-turn experience is validated — see §07, Phase 4.
